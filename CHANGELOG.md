## [Unreleased]

### Added

* Saved version 1 settings at `~/.config/kiro-gateway/config.json`, with a loopback listener, one session reference, and up to 32 exact client name to upstream model ID mappings (see [spec 0002](docs/specs/0002-local-configuration-credentials/index.md)).
* `config init`, `config check`, and `config upgrade` let you create and validate settings without a gateway token. Initialization preserves existing files. Upgrade leaves version 1 unchanged and rejects unknown versions without modification. Validation rejects oversized files, unknown or duplicate members, invalid UTF 8, and invalid field values without echoing file contents.
* `account link` reads your existing unexpired IAM Identity Center record from Kiro CLI's local SQLite store and saves only its source identifier and SHA 256 fingerprint. Linking identical bytes preserves settings exactly. Linking changed bytes, including token renewal or JSON formatting changes, clears all model mappings. Linking does not refresh credentials or establish live inference compatibility.
* `account forget` removes the session reference and all model mappings. You can repeat it safely. Kiro CLI credentials remain intact.
* Private configuration storage with ownership, permission, and symlink checks, plus atomic saves that install a complete file. Failures before installation preserve the previous file. Errors after installation report an uncertain save outcome so you can check settings before retrying.
* Local mutation diagnostics report outcome, elapsed time, and sanitized error categories on stderr. The gateway retains no diagnostic files, credential copies, or conversation content.
* A test only protocol feasibility harness covers streamed text, a tool request, a matching synthetic tool result, a followup turn, cancellation, and interruption at 256 bytes. You can exercise it with synthetic credentials and local TLS servers. Live runs require separate review and explicit launch controls (see [spec 0003](docs/specs/0003-first-claude-code-loop/index.md)).
* Combined token and selected profile snapshots let the harness read both records in one SQLite transaction, route by the profile ARN region, and stop if the linked token or pinned profile bytes change during a run. Credentials and profile pins stay in memory.
* Feasibility runs have a six attempt ceiling, time and byte limits, fixed regional destinations, and sanitized summaries. The harness holds the configuration lock and makes no automatic retry, credential renewal, or model fallback.
* Recorded all six live feasibility cases as observed on October 1, 2026, at commit `4fd0b70`, requesting `claude-opus-5.5`, with verdict `limited_candidate_observed` (see the [verification record](docs/specs/0003-first-claude-code-loop/verify.md#approved-six-case-proof-passed-october-1-2026)). Instructions remain in user content, stream end permits only tentative completion, and resolved model identity, token usage, and output token limits remain unverified. The gateway inference endpoint and a real Claude Code coding task remain pending.
* `serve --experimental-bridge` lets you enable authenticated `POST /v1/messages` with streamed or ordinary JSON responses and `POST /v1/messages/count_tokens` with local token estimates. It requires a linked session and the exact mapping `"claude-opus-5.5": "claude-opus-5.5"`. Plain `serve` keeps inference disabled (see [spec 0004](docs/specs/0004-claude-code-bridge/index.md)).
* The experimental bridge carries text, tool requests, matching tool results, and followup turns while Claude Code retains tool execution and permission decisions. Instructions become user context without guaranteed system priority or replacement. Completion is inferred, reasoning is discarded, usage is estimated, `max_tokens` is advisory, effort is ignored, beta features are unsupported, and serving model identity is unverified. Startup output and response headers disclose these limits.
* Experimental inference admits one active request, validates requests before account access, and checks a fresh token and selected profile snapshot before dispatch. Cancellation and detected stream failures stop the request without automatic replay, renewal, or model fallback. Incomplete tool calls are withheld. A whole missing frame at a clean boundary may escape detection.
* Recorded the first real Claude Code coding loop on October 2, 2026, with Claude Code `2.1.287`, Kiro CLI `2.8.0`, and requested model `claude-opus-5.5`. The separately approved run recorded `experimental_loop_observed`, with 8 dispatches in 805.64 seconds. Operator observations covered file edits, test execution, and a followup boundary test under individual permissions; cancellation, injected stream interruption, and cleanup also passed (see the [sanitized run record](internal/kiro/testdata/bridge-run-2026-10-02-04.json)). This is experimental evidence. Broader compatibility and GA acceptance remain pending.
* A development only model schema probe under the `schemaprobe` build tag prepares investigation of the declared request fields for `claude-opus-5.5`. It permits at most one combined account snapshot and one catalogue request, with 25 seconds for work and five seconds for cleanup, and cannot dispatch inference. Launch defaults off and requires a separately reviewed clean code commit, concrete plan, and explicit approval. All four GA protocol gates remain open (see [spec 0004 AC-16](docs/specs/0004-claude-code-bridge/index.md#model-schema-investigation)).
* The schema probe limits responses to 1 MiB and retains only a structural JSON report of at most 16 KiB for eight fixed paths. It distinguishes unknown paths from explicit absence, excludes raw schema and account values, and requires successful response validation and cleanup before reporting `schema_observed`. Failures stop without retry, pagination, credential renewal, model fallback, or settings changes (see the [probe guide](internal/kiro/SCHEMA_PROBE.md)).
* Recorded the selected `claude-opus-5.5` catalogue schema on October 5, 2026, with one request and completed cleanup in 1676 milliseconds. It declares `max_tokens` from 1024 to 128000, effort values `low`, `medium`, `high`, `xhigh`, and `max` with default `medium`, and adaptive thinking fields. These are structural declarations, not verified inference behavior or GA guarantees (see the [sanitized report](internal/kiro/testdata/schema-run-2026-10-05-02.json)).

* A development only `CreateResponse` discovery probe under the `responsediscovery` build tag tests one fixed request hypothesis for `claude-opus-5.5`. It permits at most one combined account snapshot and one dispatch, with 25 seconds for work and five seconds for cleanup. Launch defaults off and requires a reviewed clean code commit, exact plan, software digests, and separate approval (see [spec 0004 AC-17](docs/specs/0004-claude-code-bridge/0004-createresponse-discovery.md)).
* Discovery validates JSON, server sent events (SSE), and AWS EventStream framing within a 256 KiB response limit. It retains only a structural report of at most 16 KiB, excluding returned text, arbitrary keys, account values, and upstream identifiers. Reading continues through body end after candidate completion markers. Failed cleanup clears the body summary and terminates the dedicated process after a bounded report attempt (see the [discovery guide](internal/kiro/RESPONSE_DISCOVERY.md)).
* Recorded passing offline discovery verification and an approving independent review, covering synthetic settings, credentials, local TLS, framing, redaction, cancellation, limits, and cleanup failures. No live discovery request has run. Concrete launch preparation remains pending, and all four GA protocol gates remain open (see the [verification record](docs/specs/0004-claude-code-bridge/verify.md#offline-discovery-verification-observed-october-5-2026) and [October 6 review](docs/reviews/2026-10-06-feat-claude-code-bridge-design.md)).

### Changed

* `scripts/check` now vets and runs the tagged schema probe tests with the race detector and launch forced off. You can check the probe with synthetic settings, credentials, and local TLS without accessing your real account.
* `scripts/check` also vets and runs the tagged discovery tests with the race detector. It clears inherited `GOFLAGS` and forces both development probe launch flags off, so you can run the synthetic suites without accessing your real account.
* Updated the offline Claude Code baseline to `2.1.289` and its executable digest after the operator requested the latest release. Synthetic coding, tool result, followup, test result encoding, mutation, and retry checks pass with the race detector. Earlier live evidence remains tied to `2.1.287` (see the [new offline record](internal/gateway/testdata/claude-code-2.1.289-offline-loop.json)).
* `serve` uses the saved listener unless you supply `--listen`. Invalid saved settings block startup even with an override. Serving and settings mutations hold an exclusive process lock, so you can stop the server before changing settings and restart it to apply edits.
* Builds now require `CGO_ENABLED=1` and a C compiler for `github.com/mattn/go-sqlite3 v1.14.50`, which bundles SQLite. No external SQLite executable is required.

### Fixed

* The schema probe can hash the complete pinned native binary, which exceeds the previous 1 GiB limit. Software hashing remains bounded to 2 GiB with cancellation checks. Synthetic preflight tests now exercise matching artifacts and reject changed commands, software bytes, plan digests, code commits, dirty code, and invalid environments before account access.
* Fragmented text and tool inputs no longer repeatedly copy all accumulated content. The experimental bridge preserves its byte limits and response content while bounding accumulation costs (see the [measured synthetic results](internal/kiro/testdata/review-repair-2026-10-04.json)).
* The coding proof runner now requires two completed client turns, each with matched successful edit and test results and successful final response writes. The followup boundary test must be added on the second turn, pass on the final fixture, and fail when the upper boundary defect is introduced in a disposable copy. Missing results, cancellation, and failed or short final writes cannot satisfy the proof. This repairs the verdict checks; the earlier live observation remains tied to its original runner and client (see the [repair review](docs/reviews/2026-10-04-feat-claude-code-bridge-design.md#repair-review-2026-10-04)).
* Offline retry checks now require two observed requests for HTTP 429 and 502 when `CLAUDE_CODE_MAX_RETRIES` is absent, stopping the client at the second request, and exactly one when it is zero. Interrupted streams retain their separate one request expectation, so a missing retry can no longer silently pass the control check.
* The feasibility harness now applies its inactivity deadline to DNS resolution and connection setup. Preflight commands also bound pipe cleanup and reject expired contexts, so stalled connections or version checks cannot silently bypass those limits.
